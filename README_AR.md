# R3A AI — حزمة بداية للمنصة

هذه الحزمة تجمع واجهة HTML الحالية مع Backend أولي وPostgreSQL. إنها **حزمة تطوير قابلة للتشغيل محليًا** وليست منصة منشورة أو معتمدة لاستقبال الأموال حتى الآن.

## ما الذي يتضمنه المشروع؟
- API لتسجيل المستخدمين والدخول باستخدام كلمات مرور مشفرة وJWT قصير العمر.
- أدوار USER وADMIN، وحدود لطلبات الدخول، وHelmet، والتحقق من مدخلات API.
- قاعدة بيانات PostgreSQL عبر Prisma تشمل المستخدمين والمحافظ وطلبات الشحن والسجل المالي والحملات وتذاكر الدعم وسجل التدقيق.
- رقم مرجع تحويل فريد على مستوى قاعدة البيانات لمنع تكرار استخدام المرجع.
- اعتماد طلب الشحن داخل معاملة قاعدة بيانات، وتسجيل قيد مالي فريد لكل طلب معتمد، وتحديث الرصيد في المعاملة نفسها.
- إنشاء مشرف بأمر منفصل من متغيرات بيئة، دون كلمة مرور افتراضية مضمنة.
- واجهة `public/index.html` متصلة بمسارات تسجيل الدخول والمحفظة والحملات والتذاكر عند تسجيل الدخول إلى الخادم. الاستوديو وبعض صفحات التحليلات والكتالوج لا تزال تجريبية؛ لا توجد حملات اجتماعية أو إعلانات تُشغّل تلقائيًا.

## التشغيل محليًا
1. ثبّت Node.js 20+ وDocker Desktop.
2. انسخ `.env.example` إلى `.env` وغيّر كل القيم السرية، واجعل قيمة `POSTGRES_PASSWORD` في `DATABASE_URL` مطابقة تمامًا لها، وغيّر `JWT_SECRET` إلى سلسلة عشوائية قوية و`ADMIN_PASSWORD` إلى كلمة مرور فريدة بطول 16 حرفًا على الأقل قبل الإطلاق العام.
3. اجعل `DATABASE_URL` متوافقًا مع قاعدة البيانات المحلية. مثال compose يستخدم المستخدم `r3a` وكلمة المرور التي تحددها في `POSTGRES_PASSWORD`.
4. شغّل قاعدة البيانات: `docker compose up -d db`.
5. ثبّت الحزم: `npm install`.
6. شغّل الاختبارات الساكنة: `npm test` (لا تتطلب اتصال قاعدة بيانات).
7. أنشئ العميل: `npm run prisma:generate`.
8. أنشئ وطبّق الترحيل الأول: `npx prisma migrate dev --name init`.
9. أنشئ حساب المشرف: `npm run admin:create`.
10. شغّل API: `npm run dev`، ثم اختبر `GET http://localhost:3000/api/health`.

بديل Docker كامل: انسخ `.env.example` إلى `.env`، واضبط `POSTGRES_PASSWORD` بكلمة مرور عشوائية قوية، و`JWT_SECRET` إلى سر عشوائي لا يقل عن 32 حرفًا، و`ADMIN_PASSWORD` إلى كلمة مرور حساب الإدارة الوحيد `giedogroup@gmail.com` من خلال إعدادات الأسرار الآمنة؛ البريد مثبت في الكود ولا يمكن تغييره من التسجيل العام. ثم شغّل `docker compose up --build`. عند بدء الحاوية تُطبّق الترحيلات ويُجهّز حساب الإدارة الوحيد من `ADMIN_PASSWORD`، ثم يبدأ الخادم. لا ترفع ملف `.env` إلى Git. الترحيل الأول محفوظ في `prisma/migrations`.

## مسارات API الأساسية
- `POST /api/auth/register` — `{ "email": "user@example.com", "password": "long-unique-password" }` (12 حرفًا على الأقل).
- `POST /api/auth/login` — يعيد token.
- أرسل `Authorization: Bearer <token>` للمسارات المحمية.
- `GET /api/me`
- `GET /api/wallet`
- `POST /api/wallet/topups` — `{ "amount": 200, "providerReference": "UNIQUE-REFERENCE-1234", "senderName": "اختياري", "notes": "اختياري" }`.
- `GET /api/wallet/topups`
- `GET /api/admin/topups` — للمشرف.
- `POST /api/admin/topups/:id/approve` — للمشرف فقط، ويشترط `{ "verifiedReceived": true }` بعد التحقق المستقل من وصول المال في سجل المحفظة/مزود الدفع.
- `POST /api/admin/topups/:id/reject` — `{ "reason": "سبب واضح" }`.
- `POST/GET /api/campaigns`
- `POST/GET /api/tickets`
- `GET /api/admin/overview` — ملخص إداري للمشرف فقط.
- `GET /api/admin/tickets` و`PATCH /api/admin/tickets/:id/status` — إدارة تذاكر الدعم للمشرف فقط، مع سجل تدقيق.
- `GET /api/admin/campaigns` — استعراض موجزات الحملات للمشرف فقط.

## قواعد مهمة للمدفوعات
- الرقم المعروض للعميل: `01114887511`، ومزود المحفظة الذي حدده مالك المشروع هو اتصالات كاش. يجب التأكد من اسم المستلم وملكية الرقم داخل تطبيق المحفظة قبل التحويل. يوضح الموقع الرسمي لـ e& Egypt أن محفظة e& money تدعم تحويل واستقبال الأموال، لكن ذلك وحده لا يوفر بيانات اعتماد أو API تجاريًا لهذا المشروع.
- النموذج الحالي **لا يتصل بمزود دفع** ولا يستطيع التحقق آليًا من وصول الأموال. المراجعة اليدوية يجب أن تتم من سجل المحفظة/كشف المزود، لا من صورة إيصال وحدها. حتى الآن لا توجد بيانات اعتماد تاجر أو وثائق API مقدمة للمشروع، لذلك لا يوجد تحقق آلي، وتظل `PAYMENT_MODE=manual`. تواصل مع e& Egypt عبر قنواتها الرسمية واسأل تحديدًا عن خدمة تحصيل للتجار، وواجهات API أو Webhook موقّعة، وآلية مطابقة المبالغ والمراجع قبل بناء تكامل حقيقي.
- لا تطلب أو تخزن PIN أو OTP أو كلمة مرور المحفظة.
- قبل الإطلاق الحقيقي، اربط مزود دفع/تاجر يدعم API أو إشعارات Webhook موقعة وتسوية مرجعية، وتحقق من توقيع الإشعار ومعرّف العملية والمبلغ والعملة والحالة، مع منع إعادة التشغيل (replay) ومطابقة التحويلات.
- لا تفتح endpoint اعتماد الشحن للمستخدمين العاديين، ولا تضع مفاتيح API في الواجهة أو Git.
- راجع المتطلبات القانونية والضريبية وشروط مزود الدفع في مصر قبل قبول مدفوعات العملاء.

## الاختبارات المتاحة
- `npm test` يشغّل 14 اختبارًا ساكنًا لصياغة الخادم، ومسارات مراجعة الشحن، وقيود قاعدة البيانات، وإعدادات الأسرار وملفات النشر.
- هذه ليست اختبارات تكامل: لم يتم تشغيل PostgreSQL أو اختبار تدفق شحن كامل عبر قاعدة بيانات في هذه البيئة.

## ما يزال مطلوبًا قبل الإنتاج
1. إنشاء migration وحفظه في المستودع، ثم اختبارها على قاعدة بيانات نظيفة.
2. الواجهة متصلة بالخادم في تسجيل الدخول والمحفظة وطلبات الشحن والحملات والتذاكر، مع أدوات إدارية لملخص المنصة ومراجعة الشحن وإدارة تذاكر الدعم؛ أجزاء الكتالوج والتحليلات والاستوديو ما زالت تجريبية وتحتاج تنفيذًا إضافيًا.
3. اختبار أمني ومراجعة من مطور: سياسات CORS، TLS/HTTPS، إدارة أسرار، استعادة كلمة المرور، تأكيد البريد، جلسات/إبطال الرموز، مراقبة، نسخ احتياطية، واختبارات آلية.
4. اختيار مزود دفع فعلي وتوفير بيانات تاجر رسمية وتكامل موثق. لا توجد بيانات اعتماد أو استضافة مرفقة هنا.
5. ربط منصات التواصل عبر APIs الرسمية والصلاحيات المطلوبة؛ لا توجد مفاتيح منصات أو تشغيل حملات فعلي في هذه الحزمة.
6. نشر التطبيق وقاعدة البيانات على حسابات استضافة يملكها صاحب المشروع.

**تنبيه هندسي:** هذه نقطة انطلاق قابلة للتطوير وليست شهادة أمان أو جاهزية إنتاج. يجب مراجعة الكود واختباره قبل التعامل مع أموال أو بيانات مستخدمين حقيقية.

## النشر على Render (نسخة اختبار)

يوجد ملف `render.yaml` لتجهيز خدمة تجريبية. لا يمكن إنشاء الموقع على حسابك أو نشره نيابة عنك من هذه الجلسة لأن حسابات الاستضافة وGit غير متصلة.

1. أنشئ مستودعًا خاصًا في GitHub وارفع محتويات هذا المجلد إليه، ولا ترفع `.env` أو أي أسرار.
2. أنشئ حسابًا في Render، واختر New → Blueprint، ثم اربط المستودع واختر ملف `render.yaml`.
3. راجع الموارد والتكلفة قبل الموافقة. ملف الإعداد الحالي يستخدم موارد مجانية للاختبار فقط؛ خدمة Render المجانية قد تتوقف عند عدم الاستخدام، وقاعدة PostgreSQL المجانية تنتهي بعد 30 يومًا وفق توثيق Render. لا تستخدمها لتخزين أموال أو بيانات عملاء إنتاجية.
4. قبل أول نشر، اضبط `ADMIN_PASSWORD` من لوحة Render كسرّ (استخدم كلمة مرور قوية وفريدة؛ كلمة المرور التي اخترتها تصلح للاختبار لكن يُفضّل تقويتها قبل استقبال العملاء). عند بدء الحاوية تُطبّق الترحيلات ويُنشأ/يُحدّث حساب `giedogroup@gmail.com` تلقائيًا ويُزال دور الإدارة عن أي حساب آخر. بعد اكتمال النشر اختبر `/api/health` و`/api/ready`. لا تضع كلمة المرور في Git أو في الواجهة.
5. قبل الإطلاق، بدّل الموارد المجانية بخطة مناسبة ومدفوعة مع نسخ احتياطي، واختبر استعادة قاعدة البيانات، واضبط الأسرار في لوحة الاستضافة.
6. إذا لم ينشأ الحساب تلقائيًا بسبب إعدادات البيئة، استخدم بيئة موثوقة متصلة بقاعدة البيانات واضبط `ADMIN_PASSWORD` كسرّ، ثم نفّذ `npm install` و`npm run prisma:generate` و`npm run admin:create`. لا ترسل بيانات الاتصال أو كلمة المرور إلى أي شخص، ولا تحفظ ملف `.env` في Git.

المراجع الرسمية: [خطوات النشر على Render](https://render.com/docs/your-first-deploy)، [قيود الخطة المجانية في Render](https://render.com/docs/free)، [صفحة e& money الرسمية](https://www.etisalat.eg/portal/pages/services/eand_money_en.html).
